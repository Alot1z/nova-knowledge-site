The context addon

First, the correction

NOVA does not parse or compact context. There is no text model in it. It reads 30 floats of state and 28 floats per option and emits one scalar per option. Feeding it a smaller context changes its inputs; producing that smaller context is a different job performed by a different component.

Anyone who says "NOVA compacts your context" is describing a component that does not exist — at least not inside the decision model. This article is about the component that does exist.

Why a separate module

nova/context.py. Separate file, separate tests, separate experiment. Three reasons:

It must import without torch. The decision model needs torch and numpy. The context planner needs nothing — no numpy, no transformers, no tokenizer library. A test asserts that importing nova.context pulls in none of them, so it runs in a fresh clone on a machine with nothing installed.

It has a different failure mode. A bad decision is one wrong option. A bad compaction silently deletes the sentence the answer was in. Those need different measurements, and the compaction side needs a retention probe, not an accuracy number.

It has a different cost structure. The decision runs on every route. Compaction runs on a schedule you control. Conflating them means you cannot turn one off.

Zero parameters

The default executor is a deterministic planner. No weights, no network, no clock, no randomness. Same inputs, same plan, byte for byte. That satisfies "low model size" in the most literal way available: it adds zero.

The plan works like this. Each context item — a file, a turn, a tool result, a note — is split into sentence-or-line units. Every unit gets a score:

score = 3.0 * norm(query_hits)          relevance, IDF-weighted over the items being planned
      + 2.4 * [any query hit at all]     a flat bonus, so a short exact answer beats a long
                                         filler sentence that mentions the topic once
      + structural_bonus                 paths, identifiers, error codes, "must/never/required",
                                         trailing questions
      + 0.6 * recency                     later material, gently
      + 0.8 * framing                     the first and last units of each item
      + 6.0 * pinned                     pinned items are non-negotiable
      + 0.5 * priority                    caller-supplied
      + spread                           stop one file eating the whole budget

Then: greedy selection under a token budget, then reassembly in original order. The order step matters more than it looks. A plan that keeps the right sentences in scrambled order is worse than no plan, because the reader has to re-derive the structure that was just destroyed.

Every keep and every drop carries a reason string — query-or-structural-match, budget-selected, below-budget — so an operator can audit why a line survived.

The IDF weighting is what keeps this from being a keyword grep: a query term that appears in every file gets a low weight, because it discriminates nothing.

Measured

python -m nova.compact_experiment plans ten reader-shaped queries over this repository's own docs and code, at four budget fractions, and records reduction, retention, latency and peak memory. Corpus: 40,090 tokens, counted with tiktoken — exact, not estimated.

Peak traced memory during planning: 2.7 MB.

The retention probe is what makes the reduction mean something. Probe terms are drawn from the corpus text before the plan runs, and the report says how many survived. A reduction ratio with no retention number next to it is a number about nothing — 100% of anything can be deleted if you do not care whether the answer is still in there.

The worst case is a real finding. On the calibration query the planner keeps 2 of 4 probe terms. ECE, NLL and Brier are rarer strings than the prose around them, so sentence-level extraction finds fewer of them. Extractive selection can only keep sentences that exist; when the answer lives in one buried sentence, it is exactly where a summarizer earns its cost.

Local and online endpoints, one interface

from nova.context import Compactor, EndpointSummarizer

local = EndpointSummarizer("http://127.0.0.1:11434", "qwen2.5:3b")
online = EndpointSummarizer("https://openrouter.ai/api/v1", "some/model",
                            api_key="...")

Both speak OpenAI /chat/completions, which is what Ollama, llama.cpp's server, LM Studio, vLLM, OpenAI, OpenRouter, Together and Groq all expose. The URL decides which; the plan, the accounting and the report do not change. The experiment probes for a live endpoint and records what it found or why it did not, so a run never implies an LLM pass that did not happen.

Two constraints keep an endpoint honest:

  • It can only shrink. It is asked to rewrite the text the planner already selected. It cannot

widen the budget or resurrect dropped material.

  • Failure degrades, it does not lie. An unreachable endpoint produces the extractive plan plus

a warning. The report's executor field names the extractive planner, not the endpoint, because no call was made.

There is a test for exactly that: with summarize=False and an endpoint configured, the executor field must read extractive. Claiming an endpoint call that never happened is the kind of small lie that becomes a large one.

A bug worth recording

The first version capped units per item at 24. That is a reasonable speed knob and a dishonest default, because it silently discarded the rest of the file before budgeting — which meant tokens_before described a truncated view, and every reduction ratio computed against it was a fiction. At a 25% budget of the raw corpus, the planner reported a reduction of 0.0 and no warning, which read like "the context could not be compressed" and was actually "the planner measured itself".

Fixed by defaulting the cap to off and, when a caller sets one, reporting the truncation in plan.report()["warnings"]. It is finding F25 in the log.

The general lesson: a ratio is only as honest as its denominator. The experiment now computes its baseline as the planner's own view of the whole corpus, per query, rather than the raw character count, so the two cannot drift apart.

What this is not

Not a summarizer of record. Not a replacement for retrieval. Not a claim about anyone's token bill. A deterministic, auditable budget planner with a measured retention profile, plus an optional LLM pass that is only allowed to shorten what the planner already chose.
