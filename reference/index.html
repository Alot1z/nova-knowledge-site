PIMO is a scorer, not a generator. It takes options and a state and returns a ranking with a confidence. Everything on this page is a contract you can call directly, and every field name here is the field name in the code.

The five tools

PIMO speaks MCP over stdio and exposes five tools. Nothing needs to be registered in advance: option identifiers are opaque strings supplied by the caller.

pimo_decide

pimo_decide(state: dict, options: list[dict], request_text: str = "",
            policy: str = "BALANCED") -> dict

Scores the options you pass against the state you pass. Returns selected_option, option_scores, confidence, uncertainty, expected_utility, expected_cost, expected_latency, risk, novelty, escalate, reason_code, model_version, decision_id.

request_text is optional and defaults to empty. Passing it turns on capability discovery for that call, which costs real wall-clock time; a caller that already knows its candidates should leave it empty. See the cold-start report for the measured difference.

policy selects how cost, latency and risk are weighted against quality. The default is BALANCED.

pimo_discover

pimo_discover(query: str = "*.exe") -> dict

Enumerates locally available capabilities and returns up to 200 of them as {"id", "kind", "description"}, plus a per-source report. This is the tool that turns a machine's contents into candidate options; it is not on the decide path, because deciding over options you already hold does not need it.

pimo_telemetry

pimo_telemetry() -> dict

Cache hit counters, registry size, and the number of decisions served.

pimo_self

pimo_self(verb: str = "report", ledger: str = "artifacts/outcomes.db",
           state: dict | None = None) -> dict

PIMO applied to PIMO's own execution surfaces. verb is one of:

  • report — what is measured and what is still a prior
  • arbitrate — decide which surface should serve a decision
  • run — decide, execute the winner for real, then measure it

pimo_install

pimo_install(verb: str = "status", apply: bool = False,
             harness: list[str] | None = None) -> dict

Plans or applies installation of the agent skill, the MCP entry, and the hook. Dry run unless apply is true; every verb returns a per-harness plan so a wrapper can show it before anything is written.

The decision

decide filters to the available options, scores them, and returns the selected one together with the full score for every candidate it considered. An empty candidate set is not an error: it returns selected_option: null with uncertainty at its maximum, escalate: true, and reason_code: "no_feasible_option".

An option is available when enabled is true and availability["available"] > 0.5. Both conditions, always.

reason_code is one of novelty_gate, low_confidence_escalate, cache_cheapest_sufficient, deterministic_sufficient, local_local_model_preferred, local_tool_preferred, local_agent_preferred, quality_cost_tradeoff, or no_feasible_option.

The feature vectors

The model consumes two fixed-width vectors and emits one score per option instance. There is no fixed output vocabulary: a capability never seen during training still receives a score, because the value head reads that option's own feature row.

The state vector is 30 dimensions, in this order:

exact_hit, sem_similarity, sem_age, query_volatility, freshness_requirement, internet, net_latency, local_model, tool, agent, load, budget_remaining, cost_pressure, latency_pressure, task_risk, blast_radius, verification_required, step_count, ambiguity, complexity, novelty_prior, determinism_known, repeat_rate, recent_failure_rate, prior_success_rate, escalations, goal_type, verification_weight, cost_sensitivity, latency_sensitivity.

The option vector is 28 dimensions, in this order:

cost_financial, cost_token, cost_energy, lat_p50, lat_p95, risk_base, failure_rate, side_effect, irreversible, quality, quality_ceiling, determinism, available, health, degraded, capability_match, req_satisfied, context_fit, is_cache, is_deterministic, is_local, is_tool, is_agent, is_online, is_human, is_escalate, is_stale, hist_success.

Six heads read those vectors: value, cost, latency, risk, noise, novelty. Noise and novelty are separate heads on purpose. Collapsing them into one would let a merely unfamiliar option look like a genuinely novel one.

The exported model

The exported artefact is ONNX, not a Python pickle, so it loads anywhere without executing repository code.

Two files ship:

  • fp32 — the reference. Its graph hash is checked against the checkpoint it

was exported from, and its selections are checked against the PyTorch model it came from.

  • int8 — quantised, roughly a quarter of the size. Quantisation is allowed

to change which option is selected; the gate measures the cost instead of pretending it is free.

The gate is five terms: the graph matches its checkpoint, fp32 matches PyTorch, fp32 reproduces the same selection, int8's accuracy cost is inside budget, and latency is inside its drift budget. The ONNX contract report renders the measured values.

The performance contract

Correctness answers "is it right". Speed answers "is it worth calling", and for a machine without a GPU that is the question that decides adoption, so it gets its own published promise rather than a figure buried in a report.

The contract covers a four-core machine with no GPU, running the single-threaded CPU execution provider. For both exported graphs it publishes the session startup and the per-call inference latency, measured as the median of five batches of twenty calls rather than one percentile over a run of back-to-back calls — on a loaded machine the latter measures the scheduler as much as the graph, and the batch-to-batch spread is published alongside so a reader can see how noisy the machine was.

Those figures are written to one file and checked by re-measuring. A figure outside 0.5x to 2.0x of the published one fails the build, in both directions: a slowdown is a regression, and a measurement far faster than published means the published number is stale and every later check is being made against a promise nobody is keeping. The document and the file it quotes are written from the same measurement, so they cannot disagree.

Two things the contract deliberately does not claim: GPU execution, which has not been measured, and throughput under concurrency, since every figure here is one caller on one thread.

What is not here

The weights, the training data, the code that produces them, and the analytic world the model was distilled from are not published on this site. They live in a private repository. Accuracy quoted anywhere on this site is measured against that world, which is a ranking against other routers on one synthetic environment — not a claim about production traffic.
